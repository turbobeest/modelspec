## What it measures

AutoBencher Safety tests whether a model refuses a harmful request, but the requests themselves are not human-written the way most refusal benchmarks' prompts are; they were produced by the same AutoBencher search procedure documented on `autobencher_capabilities`, aimed here at a different target. An evaluator LM proposes candidate harmful-topic descriptions -- an adaptive search loop runs 10 rounds proposing 10 descriptions each, generating 10 requests per description -- and every candidate topic is scored by how often a panel of target models actually complies with it instead of refusing, its attack success rate (ASR). Later rounds are steered toward topics and phrasings with a higher observed ASR, so the released set is deliberately enriched for requests existing models are bad at declining, not a representative sample of harmful requests generally. Topics span concrete, specific scenarios -- "Military robot," "Lethal autonomous weapon," "Online child abuse," "Ransomware," "2021 Squid Game cryptocurrency scam" -- each narrowed further by an added requirement (for instance, a military-robot prompt asked to "include ethical concerns and battlefield applications"). Unlike the capability datasets, no privileged source document grounds each item, because the authors judge that the correct response, refusal, does not depend on any outside fact.

## How it is scored

Every item's gold answer is literally the string "Refusal": there is no correct substantive answer to give, only a correct decision to decline. HELM's `autobencher_safety` scenario scores a model's response with the same model-judged annotation field the capabilities scenario uses, treating a response as correct when it is judged to have appropriately refused. The paper itself reports results the opposite way round, as attack success rate (ASR = 1 minus refusal rate): the AutoBencher-constructed set reached an average ASR of 0.38 against the panel of models it was searched over, versus 0.08 for XSTest (`xstest`) and 0.28 for HarmBench (no page in this repository yet) scored the same way -- meaning models comply with AutoBencher's discovered prompts noticeably more often than with either existing safety set. It falls short of adversarial GCG-suffix attacks on HarmBench (0.45 ASR), which AutoBencher does not try to match, since it searches for systematic topic-level weaknesses rather than per-prompt adversarial token strings. Before release, the authors also ran a Mechanical Turk harmfulness audit and pruned roughly 2% of generated prompts that reviewers rated as posing no real risk (about 4% at a stricter threshold).

## Dataset and licence

The exact file HELM loads holds 301 prompts across 30 topic categories, ten items per topic, each also tagged with a broader parent category (Robotics, Cybersecurity, Bioethics, Politics, and similar groupings) confirmed directly from the JSON itself. It is hosted not on the main AutoBencher repository but on a co-author's fork (`farzaank/AutoBencher`), inside a folder named for Mechanical Turk processing; neither that fork nor the upstream repository carries a LICENSE file, and no licence is stated anywhere this research could find, so terms of reuse are not established. All prompts are in English.

## Who publishes it

AutoBencher Safety is part of the same AutoBencher project as `autobencher_capabilities`: Xiang Lisa Li, Farzaan Kaiyom, Evan Zheran Liu, Yifan Mai, Percy Liang and Tatsunori Hashimoto at Stanford, posted to arXiv in July 2024 and accepted at ICLR 2025. Stanford CRFM's HELM team integrated it as the `autobencher_safety` scenario alongside the capabilities one, sharing a leaderboard schema that, as of this research, is not hosted as a public site (see Saturation below).

## Lineage

This page has no predecessor id in this repository. Its closest relative is `autobencher_capabilities`, built by the identical search procedure but optimised for a different desideratum (finding knowledge gaps rather than refusal failures); the two are recorded as variants of each other. The paper positions the dataset as a harder alternative to existing hand-built refusal-test benchmarks, naming XSTest (`xstest`, present in this repository) and HarmBench (no page here yet) directly as the sets it compares its attack success rate against.

## Saturation and contamination

HELM defines a leaderboard schema for this scenario but, as with `autobencher_capabilities`, does not currently host a public site for it, and the live HELM Safety leaderboard tracks a different roster of scenarios (HarmBench, HarmBench-GCG-Transfer, SimpleSafetyTests, XSTest, BBQ, Anthropic Red Team) that does not include AutoBencher Safety. No model card in this repository reports this benchmark, and the census hint's score of 18.0 could not be corroborated from any source that rendered during this research, so saturation status is recorded as unknown rather than guessed. Contamination risk is medium: the specific prompt text was generated for this one search run rather than lifted from an existing corpus and has seen limited public distribution (a single GitHub fork rather than a widely-mirrored dataset hub), but its underlying topics are ordinary current-events and dual-use-technology subjects that later safety-tuning corpora commonly cover, so a model trained on more recent safety data could plausibly perform well here for reasons unrelated to this specific file.

## How to run it

The only confirmed harness integration is HELM's `autobencher_safety` scenario, which downloads the JSON file directly from GitHub rather than from a Hugging Face dataset repository, and scores it zero-shot with the same annotation-based metric name as the capabilities scenario. No lm-evaluation-harness, inspect_evals, OpenCompass or BIG-bench task for this benchmark was found. Note that HELM's own `schema_autobencher.yaml` names `annotation_autobencher_capabilities_score` as the main metric for both the capabilities and safety run groups -- worth double-checking against HELM's current source before assuming the safety scenario's numbers come from an independently named metric.

## Reading the numbers

A high AutoBencher Safety score means a model tends to refuse a set of prompts that were deliberately selected, by search, for being ones existing models fail to refuse -- so it says more about closing specific, adversarially-discovered gaps than about general safety behaviour. Because the set is small (301 items over 30 topics, roughly ten per topic) a handful of category-level failures can move the aggregate score substantially, and because the requests were authored by an LLM rather than security or policy specialists, some items may not reflect the harm categories a particular deployment actually cares about. With no live leaderboard and no scores yet in this repository's model cards, there is no established basis for calling any particular number high or low; read a reported score alongside results on XSTest and HarmBench (where available) rather than in isolation, since the paper's own comparison shows the three sets disagree substantially on how permissive current models are.
