## What it measures

AutoBencher Capabilities is not a fixed, human-written test; it is one output of a search procedure called AutoBencher. An evaluator language model (GPT-4-0125 in the paper) is pointed at a broad domain -- math, history, science, economics, or multilinguality -- and asked to propose several narrower topic descriptions within it, such as "the timeline of World War II" inside history. For each candidate topic the evaluator LM drafts a small batch of questions and answers using privileged information that only it sees: Wikipedia articles for the knowledge-style domains, a Python interpreter for math, and a machine-translation step for multilingual items. Each candidate topic dataset is then scored on how difficult it is for a panel of existing models, how much it spreads their accuracies apart, and how much it reorders the standard model ranking relative to existing benchmarks such as MMLU (`mmlu`). An adaptive search loop -- 8 rounds proposing 5 new topic descriptions each -- steers later rounds toward topics that score better on those properties. What ends up in the released dataset are the questions from the topics that survived this search, covering math, history, science, economics and multilingual factual knowledge (questions translated into Hindi, Italian, Greek and Russian).

The privileged source material is shown only to the evaluator LM that writes the questions, never to the model being tested, so answering correctly requires actually knowing the fact, computing the result, or understanding the translated question -- not access to whatever source the question was built from.

## How it is scored

Each item carries one gold answer produced by the evaluator LM from its privileged source. HELM's `autobencher_capabilities` scenario scores a model's free-form response with a model-judged correctness annotation (`annotation_autobencher_capabilities_score`) rather than exact string or F1 matching, and reports one accuracy number over the whole file, run zero-shot with no held-out training split. Separately from that per-model scoring, the paper ran its own quality control on the dataset itself via Amazon Mechanical Turk and found roughly 5% of the generated (question, answer) pairs to be wrong (3% for math and economics, 6.7% for history, 7.2% for science) -- a rate the authors call comparable to ordinary human-constructed benchmarks. That means a slice of any model's "incorrect" answers here plausibly reflects a bad gold label rather than a model mistake.

## Dataset and licence

The Hugging Face file HELM actually loads (`xlisali1/AutoBencher-capability.json`) holds 2,377 questions: 789 math, 426 multilingual, 424 economics, 414 science and 324 history, confirmed directly from its parquet split metadata. This does not reconcile with the paper's own rounded figure of "around 4000 examples," which totals all six of its experimental domains, including the separate safety dataset, rather than counting this one released file -- both figures are reported here since neither source resolves the gap. Neither the GitHub repository (`XiangLi1999/AutoBencher`, and its `farzaank/AutoBencher` fork) nor the Hugging Face dataset carries a licence file or licence tag, so the terms of reuse are not established; treat it as all-rights-reserved by default until the authors state otherwise. All text is English except the multilingual subject's translated questions.

## Who publishes it

AutoBencher comes from Xiang Lisa Li, Farzaan Kaiyom, Evan Zheran Liu, Yifan Mai, Percy Liang and Tatsunori Hashimoto at Stanford University, posted to arXiv in July 2024 and accepted for publication at ICLR 2025. Stanford's CRFM group folded the resulting datasets into HELM as the dedicated `autobencher_capabilities` scenario and `schema_autobencher.yaml` leaderboard schema, though as described below that leaderboard is not currently hosted publicly. Independent of the original authors, later Hugging Face uploads (`davidheineman/autobencher-knowledge-qa`, `davidheineman/autobencher-math`, and Allen Institute for AI's `allenai/autobencher-qa-33k`) show the AutoBencher method being re-run by other groups to generate further, larger question sets, though those are separate artifacts from the 2,377-question file this page documents.

## Lineage

AutoBencher Capabilities has no predecessor id in this repository; it is a search procedure applied to produce new benchmarks, and the paper's own point of comparison is existing hand-built sets such as MMLU (`mmlu`), against which it reports 22% more model errors and a 27% drop in model-ranking correlation. Its closest relative in this repository is `autobencher_safety`, built by the same search procedure and the same paper but aimed at finding prompts models fail to refuse rather than knowledge questions models get wrong; the two are recorded as variants of each other rather than as a family, since neither is a subset of the other. No successor benchmark by this name was found.

## Saturation and contamination

HELM's codebase defines a dedicated leaderboard schema for this scenario, but no live public leaderboard for it was found: it is absent from the current list of hosted suites on HELM's own homepage, and the URL pattern every other HELM leaderboard uses (`crfm.stanford.edu/helm/autobencher/latest/`) returns a 404. Neither the current HELM Capabilities nor HELM Safety leaderboard lists it either. Combined with the absence of any score for this id in this repository's own model cards, status is recorded as unknown rather than open or saturated -- there simply is no current public scoreboard to read a ceiling from. Contamination risk is medium: items are freshly generated rather than copied from an existing corpus, but they are grounded in ordinary, well-indexed Wikipedia facts, the file has been downloadable since mid-to-late 2024, and its construction reused GPT-4/Gemini/Claude-class models whose successors are plausibly trained on web crawls that could include it, though its low observed download count (14, at the time of this research) suggests limited uptake so far.

## How to run it

The only confirmed harness integration is HELM's `autobencher_capabilities` scenario, which loads the Hugging Face file at a pinned revision and evaluates it zero-shot with LLM-judged correctness as the main metric. No lm-evaluation-harness, inspect_evals, OpenCompass or BIG-bench task for this benchmark was found. One detail worth flagging for anyone re-running HELM's own configuration: `schema_autobencher.yaml` sets the *same* metric name, `annotation_autobencher_capabilities_score`, as the `main_name` for both the `autobencher_capabilities` and `autobencher_safety` run groups, which reads as if it may be a copy-paste in HELM's own schema file rather than two independently named metrics -- worth checking against HELM's current source before trusting a from-source reproduction of either scenario's numbers.

## Reading the numbers

A high AutoBencher Capabilities score shows a model does well on questions that were deliberately selected, through search, for being difficult and for separating models that look similar on standard benchmarks -- so a strong score here is more informative about narrow, adversarially-discovered gaps than a broad capability claim. Because the benchmark is a static snapshot of one search run from mid-2024 rather than a maintained, regularly re-verified test set, and because roughly 1 in 20 of its gold answers may themselves be wrong, treat any single-point score with some caution rather than as a precise measurement. With no live leaderboard, no reported scores in this repository's model cards, and no independent verification of the census hint's score of 18.0, there is currently no way to say whether a given number is high or low relative to other models -- only whether it is high or low relative to the roughly-100% ceiling implied by a mostly-correct gold set.
